## Executive Summary

StudioHub's documentation is extensive and demonstrates a strong intent toward architecture-first, DDD-driven design for an enterprise VFX/Animation/Production platform. There are high-quality conceptual and implementation-level documents covering architecture patterns (DDD, Clean Architecture, Modular Monolith), the event system, backend implementation patterns (selectors, services, querysets), ADR history (0001–0026), infrastructure, deployment, testing, security, and a roadmap.

However, the documentation currently exhibits the following systemic issues that must be addressed before any large-scale refactor:

- Multiple index/navigation files (README.md, SUMMARY.md) reference filenames and paths that do not match the repository (broken links).
- Concept duplication across layers (architecture vs backend vs api vs reference) without clear canonical sources.
- ADRs and architecture docs partially overlap — for some topics there are two ADRs describing similar decisions (notably event-driven / event bus ADRs).
- Numbering and directory prefixes are inconsistent (09-diagrams and 09-testing both exist, SUMMARY.md references other numeric names) causing ambiguous ordering and navigation concerns.
- Gaps in product/domain documentation required for a world-class VFX/Animation platform (product vision, personas, detailed domain models for Assets, Shots, Reviews, Pipeline integrations, DCC connectors, and enterprise features like vendor management and compliance runbooks).
- Documentation debt: placeholder and mismatched file names, missing diagrams, inconsistent terminology, and broken cross-references.

This audit documents the current state, enumerates every file in `docs/`, classifies each document, highlights duplicates and contradictions, lists ADR observations, identifies functional gaps for VFX/Animation domains, and recommends a safe, phased refactoring plan to reach a canonical documentation architecture.

## Contradictions & Tension Points (examples)

The audit found multiple places where different documents give conflicting guidance (sampled statements and locations):

1) Business logic placement
- docs/02-architecture/service-layer.md: "Business logic belongs in Services."
- docs/02-architecture/ddd.md: "Core business invariants belong in domain models/aggregates."
- docs/03-backend/services.md: Implementation examples putting logic in services and managers.

Potential resolution: Define a clear canonical guideline that composes these: "Domain invariants belong in domain model (aggregates/entities); orchestrating workflows and use-cases belong in Services/Use Cases; persistent concerns in Repositories/Managers." Document this canonical policy in 02-architecture/overview.md and create a short, authoritative cheat-sheet.

2) Event publication timing
- docs/03-backend/events.md and docs/02-architecture/event-system.md both stress publish-after-commit. ADRs too. However, some implementation examples in backend docs omit on_commit usage and imply immediate dispatch.

Potential resolution: canonical rule: publish on_commit for events dependent on DB state; document exceptions and examples in 03-backend/events.md.

3) Logging location and responsibility
- infra logging suggests central logging agent configuration; operations runbooks document retention and SLOs; security requires immutable audit logs — no single canonical owner is specified.

Potential resolution: create a small "Logging & Audit" canonical doc under 12-reference/ or 11-operations that maps responsibilities: security (audit policy), infra (collection/agents), operations (retention, runbooks), development (how to emit logs).

For each contradiction found, create a lightweight ADR or a short RFC describing the canonical approach and link existing documents to it.
