# Review pipeline: contracts

Each entry is the API before and after one change. Paths are under `/api/v1/`. A contract is written before the code and changed only with the owner's approval.

## RP-1 Data model cleanup

| ID | Where | Before | After |
|---|---|---|---|
| C-RP-01 | Every version response: `GET versions/`, `archived/`, `{id}/`; the answers to `POST versions/`, `PATCH`/`PUT versions/{id}/`, `publish/`, `unpublish/`, `promote/`, `add-to-playlist/` and any other action that returns the version | Six JSON lists: `reviews`, `playlists`, `notes_list`, `media_items`, `attachments`, `activity`. They were stored copies (D-18), not rebuilt from the records, and only `playlists` was ever written to. | The six keys are **left out**. `publishing_info` and every other field are unchanged. The reviews and playlists that hold a version are read with C-RP-03 and C-RP-04; its history is read from the audit trail, as the frontend already does. No write accepted these keys before, and none accepts them now. |
| C-RP-02 | `POST versions/{id}/add-to-playlist/` | Added a `PlaylistEntry` and appended `{playlist_id, playlist_name}` to the version's `playlists` JSON, even without a `playlist_id`. | Adds the `PlaylistEntry` only. Request, permissions, errors and status code are unchanged. The answer is the version (C-RP-01 shape). |
| C-RP-03 | `GET reviews/` | No way to ask which reviews show a version. | Optional query parameter `version_id`. It lists the reviews with a live item (`ReviewItem`, not deleted) for that version. An empty value means no filter. An unknown or malformed value gives an empty list, never a 400. It combines with every other filter and keeps the list's own narrowing. Nothing is written. |
| C-RP-04 | `GET playlists/` | Filters `status`, `project`, `client_only` only. | The same three, plus optional `version_id`: the playlists with a live entry (`PlaylistEntry`, not deleted) for that version. Same rules as C-RP-03. |
| C-RP-05 | `POST reviews/{id}/comments/` and `POST reviews/{id}/annotations/` | No way to say which version of the review a comment or a drawing is on. | Optional `version_id` (UUID or `null`). When it is given, it must be a version shown in this review (a live `ReviewItem`). Otherwise the answer is **400** `{"version_id": ["This version is not in the review."]}`, also for a version of another project or an item that was removed. A malformed UUID gets the serializer's own 400. A reply (`parent_id`) takes its thread's version: leaving `version_id` out, or naming the same one, is accepted; naming another is **400** `{"version_id": ["A reply is on its thread's version."]}`. Leaving it out of a new comment or annotation keeps it on the whole review (`version_id: null`), as before. |
| C-RP-06 | Comment and annotation shapes: the answers to C-RP-05, and `comments[]` (with `replies[]`) and `annotations[]` in the review detail and in every action that returns the review | No version. | Each comment, reply and annotation carries `version_id` (string or `null`). Rows written before RP-1 are `null`. Nothing else in the shapes changes. |

The column drop of PLAN WP 1.6 (migration `production` 0004) changes no API beyond C-RP-01.

## RP-2 Notes: replies, links, a task

Paths are under the project-scoped mount, `projects/{project_id}/notes/` (the frontend calls it through the `/api/organizations/projects/{project_id}/` alias). Every route keeps `external_allowed=False`: a partial (client or vendor) member gets 404, as today. "Visible" means the note is in the caller's list under the narrowing of Q-RP-13. Who may edit, change the status and delete follows Q-RP-11 and Q-RP-12 (both A, [DECISIONS.md](DECISIONS.md#rp-2-answers)).

| ID | Where | Before | After |
|---|---|---|---|
| C-RP-07 | `POST notes/` | Accepts `entity_type`, `entity_id`, `entity_code`, `entity_name`, `status` and the author fields as sent; nothing is checked against the records. | Also accepts `links` (a list of up to 20 `{entity_type, entity_id}`; types per Q-RP-14) and `task_id` (UUID or `null`). The old `entity_type` + `entity_id` pair still works and is the first link; `entity_type: "Project"` or none means no link. Every link and the task must be a live record of this project that the writer can see under the narrowing of its own list route, or **400** `{"links": ["One of these records is not in the project."]}` or `{"task_id": ["This task is not in the project."]}`, the same for a record that does not exist. A repeated link is stored once; more than 20 is 400. `entity_code` and `entity_name` are ignored and written from the record. `status`, `addressed_by` and `addressed_at` are ignored: a new note is `Open`. The author fields are ignored, as today. The answer is 201 with the C-RP-08 shape. Permission `note.create`, unchanged. |
| C-RP-08 | The note shape: every note in the answers of C-RP-07 to C-RP-12 | The 23 keys of `ProjectNoteSerializer`. | The same keys, plus `parent_id` (string or `null`), `links` (a list of `{entity_type, entity_id, code, name}`, in the order written; a reply's is empty), `task_id` and `task_code` (strings or `null`), and `reply_count` (live replies; 0 on a reply). The four `entity_*` keys mirror the first link, or stay `"Project"`, `""`, `""`, `""` when there is none. A note written before RP-2 whose record could not be resolved (PLAN WP 2.6) keeps its stored `entity_*` values and has `links: []`. |
| C-RP-09 | `GET notes/` | Every note of the project, searchable and orderable. | **Threads only**: replies are left out. New optional filters: `entity_type` + `entity_id` (the notes with that record as any of their links), `task_id`, `status`, `author_id`. An unknown or malformed value gives an empty list, never a 400. Search, ordering, paging and narrowing are unchanged. |
| C-RP-10 | `GET notes/{note_id}/` (new) | No route. | The C-RP-08 shape of one thread, plus `replies` (oldest first, live only, each in the C-RP-08 shape). A reply's id answers with its thread. A note that is deleted, of another project, or not visible is **404**. Permission `project.view`, as the list. |
| C-RP-11 | `POST notes/{note_id}/replies/` (new) | No route. | Body `{body}` (required, not blank). The reply is stored on the thread's root (a reply to a reply goes to the root), with the thread's project, no links, no task, the caller as author and `status` `Open`. 201 with the reply in the C-RP-08 shape. 404 as in C-RP-10. Permission `note.create`. |
| C-RP-12 | `PATCH notes/{note_id}/` (new) | No route. | Any of `subject`, `body`, `category`, `priority`, `tags`, `links` (replaces the list), `task_id`, `timecode_ref`, `frame_number`, checked as in C-RP-07; a reply takes only `body`. Who may (Q-RP-11 = A): the author of the note, or a holder of `note.update`; else **403**. 200 with the C-RP-08 shape. 404 as in C-RP-10. |
| C-RP-13 | `POST notes/{note_id}/status/` and `DELETE notes/{note_id}/` (new) | No routes. | `status/` takes `{status}`: `Addressed`, `Closed` or `Open`. The server writes `addressed_by` (the caller's name) and `addressed_at` (now) on `Addressed`, keeps them on `Closed`, and clears them on `Open`. A reply has no status: 400. Who may (Q-RP-11 = A): the author, the assignee of the note's task, or a holder of `note.update`; else **403**. 200 with the C-RP-08 shape. `DELETE` soft-deletes a thread with its replies, or one reply; who may (Q-RP-12 = A): the author while no one else has replied, or a holder of `note.delete`; else **403**. 204. Both 404 as in C-RP-10. |

Details settled while building RP-2 (no change to the rows above; the owner is told in [rp-2-verification.md](rp-2-verification.md)):
- Every 400 keeps its field-keyed message as written above. Like every answer of this API, it also carries the `error` object (`code`, `request_id`).
- `links[].code` and `links[].name` are the record's own values at read time, so a renamed shot shows its new code. Archived records still answer, so an old note keeps saying what it was about. The `entity_*` columns are written once, from the first link, when the links are written.
- When both the old pair and `links` are sent (C-RP-07), the pair comes first, and a repeat is kept once.
- The project check applies to every caller, superusers and members of several projects included. Narrowing never widens it.
- A reply (C-RP-11) is stored with `subject` `Re: <thread subject>` and the thread's `category`.
- A `PATCH` of a reply naming anything but `body` (C-RP-12) is **400** `{"detail": ["A reply takes only its body."]}`.
- A reply has no replies of its own, so its author may always delete it (C-RP-13).
- No notes route lets in a partial member: client, vendor, or bound to a show or a department. All of them get 404 (`user_has_full_project_access`), as the list already did before RP-2. Q-RP-13 therefore changes nothing on these routes.

## RP-3 Approval roll-up

Approved 2026-11-12 with Q-RP-15 to Q-RP-18 = A ([DECISIONS.md](DECISIONS.md#rp-3-answers)).

| ID | Where | Before | After |
|---|---|---|---|
| C-RP-14 | Every project response (`GET projects/`, `{id}/`, the answers to `POST`, `PATCH`, `PUT` and the clone) and the project writes | No per-project switch for approvals. | New key `approve_task_on_version_approval` (boolean, default `false`) in every response, readable by everyone who can read the project. Writable on create (`project.create`) and update (`project.update`), refused as today without them. Anything but a boolean is a field-keyed 400. Every other key is unchanged. |
| C-RP-15 | The effect of a version moving to `Approved` (`PATCH versions/{id}/`, the bulk status change, `POST versions/{id}/promote/`) | Only the version changes. | No request or answer changes. When the version's project has the switch on and the version has a live task that is neither `Approved` nor `Archived`, the task moves to `Approved` once the approval has committed. Its status history names the version's approver, with the reason `Version <code> approved`. A failure of this step is logged and never changes the approval's answer. Leaving `Approved` later does not touch the task (Q-RP-16). |

Details settled while building RP-3 (no change to the rows above; the owner is told in [rp-3-verification.md](rp-3-verification.md)):
- There is no server-side project clone. The frontend's Duplicate creates a project from the old one's settings, and now copies the switch.
- Versions have no bulk status change (no `bulk_update_fields` on versions). C-RP-15's routes are `PATCH versions/{id}/` and `POST versions/{id}/promote/`.
- Promoting a version that is already `Approved` moves no status, so it rolls nothing up. The roll-up happened when the version was approved.
- A non-boolean is the usual field error, `{"approve_task_on_version_approval": ["Must be a valid boolean."]}`. The API reads `"true"`, `1` and the like as booleans, as for every boolean field.
- The switch is not in `EXTERNAL_HIDDEN_FIELDS`: a client or vendor member who can read the project sees it. It is a workflow setting, not money or people.
- Turning the switch on is not retroactive: versions approved before do not approve their tasks.
- The task's history row has no override kind, so the roll-up is not logged as `status_override_used`.

## RP-4 Publishing depth

Approved 2026-11-12 with every recommendation of Q-RP-19 to Q-RP-23 ([DECISIONS.md](DECISIONS.md#rp-4-answers)). Paths are under `/api/v1/publishing/`. The publishing app's own contracts (`docs/publishing/CONTRACTS.md`) gain DOM-PUB-07, DOM-PUB-08 and API-PUB-18 to API-PUB-21 when RP-4 is built.

| ID | Where | Before | After |
|---|---|---|---|
| C-RP-16 | `POST files/`, `POST files/bulk-register/` (each item), `GET files/{id}/`, new `GET files/{id}/dependencies/` | No dependencies. | The body takes `upstream_ids` (a list of file ids, at most 50, optional). Each must be a live file of the same project that the caller can read and that is not `Revoked`; otherwise a 400 `{"upstream_ids": [...]}` names the bad ids, and nothing is registered (a bulk item fails alone, as `invalid`). Dependencies are written with the file and never changed (Q-RP-19). An identical retry must send the same set, or it is a 409 `path_already_registered`. The file shape gains `upstream_count` and `downstream_count`. `GET files/{id}/dependencies/` answers `{"upstream": [...], "downstream": [...]}`, direct links only, each row `id`, `storage_root`, `relative_path`, `role`, `file_type`, `status`, `version_id`, `version_code`. Narrowed like the file (a 404 identical to an unknown id). |
| C-RP-17 | New `GET files/loader/` | No route from a shot, asset or task to its files. | Query: exactly one of `shot`, `asset`, `task` (an id); optional `file_type` (code), `role` (default `main`), `which` = `latest` (default), `approved`, `hero`. The answer is a list, one row per stream (the task, or the entity for versions with no task) and per file type and role: the file shape, plus `version` (`id`, `code`, `version_index`, `status`, `is_hero`) and `task` (`id`, `code`, or `null`). Within a stream, the newest live published version (by `version_index`) that has a `Registered` file of that type and role wins; `approved` takes only `Approved` versions, `hero` only the hero. The file is that version's latest of the role. Missing or several entity parameters, or a malformed id, is a 400. An entity the caller cannot reach is a 404. `publishing.view`. |
| C-RP-18 | New `/path-templates/` (list, create, read, update; no delete, `is_active` retires), new `GET files/resolve-path/`, and the effect on registration | `relative_path` is free text. | A template has `project` (`null` for the studio default), `file_type` (code), `role`, `storage_root` (code), `pattern`, `enforce` (default `false`), `is_active`. One active template per (project, file type, role). The project's template wins over the studio's. Unknown tokens, a pattern whose sample breaks the path rules, or a second active template are a 400. `publishing.template.manage` writes; `publishing.view` reads. `resolve-path?version_id=&file_type=&role=` answers `{"template_id", "storage_root", "pattern", "relative_path", "enforce"}`, with `{name}` left in the path, or 404 when no template applies. Registration: with a matching template whose `enforce` is on, a different root is a 400 on `storage_root` and a path that does not match a 400 on `relative_path` (`Does not match the path template: <expected>`); `error.code` is `validation_error`, as for every 400. Without one, registration is unchanged. |


Details settled while building RP-4 (the owner is told in [rp-4-verification.md](rp-4-verification.md)):
- One migration, `publishing` `0003_rp4_file_dependencies_path_templates`, holds both tables (the plan said two).
- A template mismatch is an ordinary field error. The plan's `path_template_mismatch` code is not in the answer: every 400 here carries `error.code` = `validation_error`, and a code of its own would need a change to the core exception handler. C-RP-18 above says so.
- An unknown, foreign or unreadable upstream id all get one message, `Unknown upstream file: <id>`. A member who may register files but not read them (bound to a show or a department, or a client or vendor member) therefore cannot name any upstream. A list that is not a list, a malformed id and a repeated id are 400s on `upstream_ids`.
- The upstream rows are locked (`SELECT … FOR UPDATE`, in id order) while the links are written, so an upstream cannot be revoked between the check and the insert.
- The loader is not paginated: it answers a list. An unknown `file_type` code answers an empty list, not a 400. Rows come task-less stream first, then by task code, file type and role. It does not skip files whose checksum is `mismatch` or `missing`; each row carries `checksum_state`.
- `resolve-path` with an unknown or unreadable version is a 400 on `version_id` (as registration is), and a template that cannot be filled for the version (a `{asset}` token on a shot's version) is a 400 on `version_id` naming the token.
- Templates: PATCH only (no PUT), no DELETE. A project template needs the writer to be a full member of the project (`Unknown project.` otherwise). The list takes `project_id=studio` for the studio's templates only. A file type extension written with a dot (`.abc`) fills `{ext}` without it.
- Publishing reads Production only through its selectors (`VersionSelector`, `ShotSelector`, `AssetSelector`, `TaskSelector`, `ProjectSelector`), as the dependency-direction test requires (delivery-pipeline X-03).
